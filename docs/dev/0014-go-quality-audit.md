## Findings (per category)

### 1. Error handling

The error-handling discipline in cascade is strong. Every `error` return is wrapped with `%w` when context is added; sentinel errors are package-level `var Err…`; typed errors (`*ExitError`, `*ParseError`, `*GitDiffError`) implement `Error()`, `Is(target)`, `Unwrap()` consistently and use pointer receivers per EH-08. Public APIs return the `error` interface, never a concrete `*MyError` (no IM-17 / TD-15 typed-nil hazards). `errors.Is` and `errors.As` are used throughout; no `strings.Contains(err.Error(), …)` matches anywhere in the tree (verified by grep).

The findings here are about citation accuracy in source-code comments, not about behavior.

### 3. API design

Public packages (`pkg/golist`, `pkg/depgraph`, `pkg/changeset`) expose minimal, behavior-named surfaces. Functional options (API-06) are used consistently: `golist.WithDir`, `golist.WithEnv`, `golist.WithGoBin`, `changeset.WithModuleRoot`. Constructors `Build`, `Run`, `Resolve` return concrete types (`*Graph`, `[]Package`, `[]string`) — never interfaces (API-11 ✓). Errors travel as the `error` interface (API-23 ✓; TD-15 ✓). No package-level globals beyond:

- The seam variables (`runGoList`, `runGitDiff`, `runGoListWrapper`, `getCwd`, `signalContext`, `readBuildInfo`) — unexported, see Systemic finding S-1.
- The build-metadata vars in `internal/project` (`Version`, `GitCommit`, `GitBranch`, `GitSummary`, `BuildDate`) — exported as documented ldflags injection targets, populated once at link/init time, not mutated at runtime by production code.
- The `Err…` sentinels (`ErrGoNotFound`, `ErrGoListFailed`, `ErrParseFailed`, `ErrGitDiffFailed`) — these are the *intended* public API contract.

The `applyOptions` / `config struct` / `Option func(*config)` pattern is internally consistent across `pkg/golist` and `pkg/changeset`. No findings under §3 beyond the systemic seam-pattern observation.

### 4. Interfaces and methods

No interfaces are exported by cascade's public packages (the producers expose concrete `*Graph`, `[]Package`, `[]string`); consumers (`internal/cli/cli.go`'s `runPipeline`) use them directly. This satisfies IM-01/IM-02 cleanly. There are no `IXxx` or `XxxInterface` Java-style names (AP-30 ✓). No typed-nil error returns anywhere (IM-17 / TD-15 ✓; verified by reading every error-returning function).

Receiver consistency (IM-12 / TD-09): every method type uses pointer receivers consistently:

- `*Graph` — `Has`, `DirectImports`, `DirectImporters`, `RevDepClosure`, `Stats` all on `*Graph`. ✓
- `*ExitError`, `*ParseError`, `*GitDiffError` — `Error`, `Is`, `Unwrap` all on the pointer. ✓
- `*prefixWriter` (test helper) — `Write` on the pointer. ✓

The only non-pointer methods I encountered are the test helpers and the value-typed `Stats` (returned by value, no methods), both correct per TD-09's "small immutable POD" exception.

> Note on the audit prompt's "TD-09 / IM-04" pairing for receiver consistency: in the loaded substrate, **IM-12** is the receiver-consistency rule ("Be Consistent — All Methods on a Type Use the Same Receiver Kind"); **IM-04** is `-er` suffix naming for single-method interfaces; **TD-09** is "Choose Pointer vs. Value Receivers Based on Type Shape." The audit-prompt text has a citation drift (matching the M3 retro's note about IM-04 cite-vs-content). The cascade code itself adheres to IM-12 + TD-09; no findings here.

### S-2: The seam-pattern (package-level function vars overridden in tests) — 6 instances

| Variable                              | File                                  | Cited substrate                                  |
|---------------------------------------|---------------------------------------|--------------------------------------------------|
| `runGoList`                           | `pkg/golist/golist.go:100`            | (production seam)                                |
| `runGitDiff`                          | `internal/cli/seam.go:30`             | (production seam)                                |
| `runGoListWrapper`                    | `internal/cli/cli.go:88`              | (production seam over `golist.Run`)              |
| `getCwd`                              | `pkg/changeset/changeset.go:51`       | (production seam over `os.Getwd`)                |
| `signalContext`                       | `internal/cli/cli.go:94`              | (production seam over `signal.NotifyContext`)    |
| `readBuildInfo`                       | `internal/project/version.go:105`     | (production seam over `debug.ReadBuildInfo`)     |

**Pattern**: Cascade systematically uses the package-level-function-variable seam to make `os/exec`, `os.Getwd`, `signal.NotifyContext`, and `runtime/debug.ReadBuildInfo` testable without subprocess-spawning or external-state setup. The substrate's **AP-08** (`SHOULD-AVOID`) names this exact pattern: "Avoid mutating global variables, instead opting for dependency injection. This applies to function pointers as well as other kinds of values."

**Why cascade does this anyway**: The structural alternative (passing the function as an interface or `func` parameter) would either (a) make every public Run/Resolve signature longer and testing-shaped, or (b) require an exported `Runner` interface that consumers don't need. The current shape — production calls `Run(ctx, …)` directly; tests swap the unexported package-global — keeps the public API clean.

**The latent risk**: AP-08's rationale is "parallel tests collide." Cascade's mitigation is *not* to make the seams parallel-safe; it is to *not run tests in parallel* (zero `t.Parallel()` in the tree; see F-6). This is a real, working compromise but it depends on a discipline that isn't enforced anywhere — a future contributor adding `t.Parallel()` to even one test would expose all six seams simultaneously.

**Recommendation (systemic)**:
1. Add a one-line note at the top of every seam-using `_test.go` file: `// Tests in this file mutate package-level variables. Do not call t.Parallel() in this test file or any test that exercises these variables.`
2. Optionally, document the seam pattern as a project-level convention in CLAUDE.md's "Testing conventions" section, naming AP-08 explicitly and the rationale for accepting the deviation.
3. Consider a unit test or `go vet`-style linter (custom analysis) that fails the build if any test file using `runGoList`/`runGitDiff`/etc. also calls `t.Parallel()`. This is a structural enforcement that would make the discipline durable.

(F-6 already covers the immediate documentation gap; this systemic finding is the broader frame.)

## What worked well (Safety-II)

A reader who has seen one knows all three. The compile-time assertions at `pkg/golist/golist.go:235-236` (`_ error = (*ExitError)(nil)` etc.) make the contract grep-visible.

2. **Doc-comment discipline exceeds typical Go projects.** Every exported name has a doc comment that starts with the identifier. Every package has a `doc.go`. Internal comments explain the *why*, not the *what* (`internal/cli/cli.go:140-156`'s explanation of why `cfg.root` is absolutized once at the CLI layer, with the bug-#12 cross-reference, is a particularly good example of DC-09 discipline). 3. **The five-seam pattern is consistently applied.** `runGoList` (golist), `runGitDiff` (cli), `runGoListWrapper` (cli's wrap-of-golist for substitution at the cli boundary), `getCwd` (changeset), `signalContext` (cli), `readBuildInfo` (project). Each has a `default*` production implementation, a `with*Seam` test helper using `t.Cleanup` for save/restore, and a one-paragraph comment at the variable declaration explaining the rationale. 4. **Coverage discipline is honest.** I sampled three places where the seam is the only way to cover an exec branch: `pkg/golist/seam_test.go:48-67` (`TestRun_UnexpectedExecError`) drives the `classifyRunError` "neither cancelled nor *exec.ExitError nor exec.ErrNotFound" fallthrough; `internal/cli/seam_test.go:237-272` (`TestClassifyGitDiffError`) drives all three branches of the cli classifier; `internal/project/version_test.go:373-409` (`TestReadBuildInfoFallback`) drives both `ok=true` and `ok=false` of `debug.ReadBuildInfo`.
